1. INTRODUCTION                                   *atom-repeat-introduction*

atom-repeat.nvim records top-level |CmdAtom| events after setup and presents
them as retrospective macros. Recording does not need to be started before an
edit. A history range can be selected after the edit and replayed at another
cursor position.

REQUIREMENTS ~

atom-repeat requires a Neovim build with the CmdAtom event. It has no runtime
dependencies and does not emulate CmdAtom on older Neovim versions.

==============================================================================
2. SETUP                                                   *atom-repeat-setup*

Setup is required and starts history capture: >lua

    require("atom-repeat").setup({
      capture_lua_prompts = true,
      history_size = 500,
      max_buckets = 20,
      max_consecutive_motions = false,
      recipes = {
        max_items = 20,
        persist = true,
        -- path = vim.fs.joinpath(vim.fn.stdpath("state"),
        --   "atom-repeat", "recipes.mpack"),
      },
      ui = {
        height = 12,
      },
    })
<
`capture_lua_prompts` enables wrappers for vim.fn.getchar and vim.fn.getcharstr
to include consumed keys in the triggering Insert mapping.
`history_size` is the entry limit for each project/branch bucket.
`max_buckets` is the least-recently-used bucket limit.
`max_consecutive_motions` retains only the first N Atoms in a consecutive run
of h, j, k, l, w, or b. The default false keeps all motions. Use 0 to omit them. A
single-key callback mapping on one of those LHS keys also counts as navigation.
A different Atom resets the run, and a counted command such as 3j is one Atom.
`ui.height` is the bottom history split height.
`recipes.max_items` limits unnamed recipes for each project/branch.
`recipes.persist` enables MessagePack persistence. `recipes.path` defaults to
`stdpath("state")/atom-repeat/recipes.mpack`.

Capacity and height values must be positive integers. The motion limit is a
non-negative integer or false. Unknown options are errors. Calling setup again
preserves history and reapplies the configured limits.

The public Lua functions are: >lua

    require("atom-repeat").open()
    require("atom-repeat").replay_last()
    require("atom-repeat").select()
<
Both require setup to have run first.

Capture begins when setup is called. Lazy-loading is supported, but actions
that occurred before setup cannot be recovered.

==============================================================================
3. HISTORY UI                                           *atom-repeat-history*

Run |:AtomHistory| after placing the cursor where replay should start. A
12-line `botright` horizontal split opens by default. Rows are ordered oldest
to newest and contain:

    sequence  type  action  buffer

The initial cursor is on the newest entry. The window bar shows the project
and branch for the snapshot.

History buffer mappings:

    <CR>    Replay the current row.
    V       Start native Visual-line selection.
    <CR>    In any Visual mode, replay every included row chronologically.
    dd      Cut the current row (accepts a count).
    d, x    In Visual mode, cut the selected rows.
    yy      Copy the current row (accepts a count).
    y       In Visual mode, copy the selected rows.
    p, P    Paste after or before the cursor (accepts a count).
    q       Close and return to the origin window without replaying.

Cut and copy use a history-UI-local register and never modify Vim registers.
These edits change only the open replay recipe, not stored chronological
history. Visual p/P replaces the selected rows while preserving that register.
Close with q to discard the recipe; <CR> replays its displayed order.

Running :AtomHistory again while the history buffer is current refreshes the
snapshot. Only one history UI can exist in the editor. Opening it from another
tab closes the old instance. An empty bucket produces a notification without
opening a split.

The origin cursor is tracked by an extmark. Replay is rejected while keeping
the UI open if the origin window, buffer, project, or branch changed.

==============================================================================
4. REPEAT                                                 *atom-repeat-repeat*

Use |:AtomRemember| to save recent actions and arm dot immediately. Finishing
a recording with qa ... q also arms dot with the recorded keys. The snapshot
contains the newly performed input even when appending to a register.

The current ReplayGroup is stored separately for every
project/branch bucket. Repeat it once with |:AtomReplayLast| or map the provided
Plug target: >lua

    vim.keymap.set("n", "g.", "<Plug>(AtomReplayLast)")
<
The Plug mapping honors |v:count1|. :AtomReplayLast runs the active group once,
or repeats the latest captured edit when there is no active group. For example,
type ciwtest<Esc>, move to another word, and run :AtomReplayLast.
Use |:AtomRemember| to save history actions for |:AtomReplaySelect|.
Running a saved recipe from the selector makes it the active group.

Use :AtomRecordStart wrap to start an explicit recording. Edit normally and
run :AtomRecordEnd to save it. Run :AtomReplay wrap at another cursor position
to execute it. Names are single words scoped to the recording's starting
project and branch. Saving an existing name replaces its previous recipe.
Omit the name to keep the current recording in memory for this session.
Use |:AtomReplayLast| or |.| to replay it.

Use toggle_recording() to bind start and finish to one key: >lua

    vim.keymap.set("n", "<leader>qr", require("atom-repeat").toggle_recording)
<
Pass an optional name when starting a named recipe.

Bind replay_temporary() to replay a temporary recording with @@: >lua

    vim.keymap.set("n", "@@", require("atom-repeat").replay_temporary)
<
It uses native |@@| when there is no active temporary recording.

Use the recording status as a lualine component: >lua

    { function() return require("atom-repeat").recording_status() end }
<
It shows REC wrap for a named recording, REC for a temporary recording,
and REC @a for a native recording in register a. It is hidden when idle.

After a captured mapped edit, |.| runs the mapping again with its input. A
count or register supplied to |.| overrides the original prefix. Ordinary edits
use native dot. After a recipe replay succeeds, |.| repeats the recipe and a
count selects how many times to run it.

An existing Normal-mode `.` mapping keeps precedence. Bind
`<Plug>(AtomRepeatDot)` to another key to use automatic mapped-edit repeat.

Other plugins may register their own repeatable <Plug> mappings after making a
change: >lua

    require("atom-repeat").set_repeat("<Plug>(MyAction)", {
      count = vim.v.count,
      register = vim.v.register, -- optional
    })
<
The registration is associated with the current buffer and |b:changedtick|.
`set_repeat()` returns false if the dot backend is unavailable.
`invalidate_repeat()` clears the current plugin registration.
This repeat-only API initializes lazily and does not require CmdAtom setup.
The standalone module API is `require("atom-repeat.dot").setup()` and `.set()`.
If vim-repeat already owns `.`, its `repeat#set()` backend is reused. Other
existing dot mappings are preserved.

5. RECIPE LIBRARY                                        *atom-repeat-recipes*

Every successful replay from |:AtomHistory| is saved in a project/branch MRU
library. From the history window, s saves the current row or Visual selection
without executing it. Identical unnamed recipes are moved to the front. The
library retains `recipes.max_items` unnamed recipes per bucket. Named recipes
remain available until deleted.

Use |:AtomReplaySelect| to open the current bucket. Rows show a persistent ID,
creation time, Atom count, and a preview. Selector mappings:

    <CR>    Replay the current recipe at the selector's origin cursor.
    dd      Delete recipes (accepts a count).
    d       In Visual mode, delete selected recipes.
    yy      Copy recipes (accepts a count).
    y       In Visual mode, copy selected recipes.
    p, P    Paste after or before the cursor (accepts a count).
    q       Close the selector.

Selector cut/copy uses a dedicated register and does not touch Vim registers.
Unlike history recipe edits, selector edits change the saved library and are
persisted immediately. Pasted copies receive new recipe IDs.

Persistence uses binary-safe MessagePack and an atomic temporary-file rename.
It is enabled by default. Disable it with `recipes.persist = false`.

==============================================================================
6. COMMANDS                                               *atom-repeat-commands*

                                                        *:AtomHistory*
:AtomHistory           Open or refresh the current history snapshot.

                                                        *:AtomRemember*
:AtomRemember [N]      Save the last N actions (default 1) for |.| and
                      |:AtomReplayLast|. Execution starts on replay.

                                                     *:AtomRecordStart*
:AtomRecordStart [name]
                      Start a native key recording. Omit the name for an
                      in-memory macro.
                                                       *:AtomRecordEnd*
:AtomRecordEnd         Stop the recording and make it active for
                      |:AtomReplayLast|. Named recordings are saved in
                      |:AtomReplaySelect|.
                                                    *:AtomRecordCancel*
:AtomRecordCancel      Stop the recording and discard its captured keys.
                                                          *:AtomReplay*
:AtomReplay {name}     Run a named recipe in the current project and branch.

                                                      *:AtomReplayLast*
:AtomReplayLast        Replay the active group or latest captured edit once.

                                                    *:AtomReplaySelect*
:AtomReplaySelect      Open the current bucket's saved recipe selector.

                                                     *:AtomReplayClear*
:AtomReplayClear       Clear the current bucket's saved recipes and active group.
:AtomReplayClear!      Clear all saved recipes and active groups.

                                                    *:AtomHistoryClear*
:AtomHistoryClear      Clear the current bucket's history and active group.
:AtomHistoryClear!     Clear all in-memory history and active groups. Saved
                      recipes remain in |:AtomReplaySelect|. Session sequence
                      numbers remain monotonic.

7. REPLAY SEMANTICS                                     *atom-repeat-semantics*

Each captured CmdAtom is one row. Recording start/stop controls are omitted. Nested composite `atoms` and all
other structured fields are deep-copied without flattening or payload limits.

Replay uses the action's input (`lhs`) with mappings enabled. When observable
through |vim.on_key()|, typed counts, registers, and Insert-mode keys supplement
the input reported by CmdAtom. A changed mapping runs its current definition.
If it was removed, the LHS is ordinary input in the current mode.

When the input is missing or represents a native dot repeat, replay uses
resolved `keys` without remapping. Saved recipes retain their stored strategy.
An explicit empty `keys` value marks an unreplayable atom.

The whole range is validated before replay. An unsupported entry prevents all
execution. A runtime error stops the remaining queue, but changes made by
earlier entries are not rolled back.

Initial history replay starts in Normal mode at the cursor snapshot. Stored
Visual Atom keys recreate their own selection. An existing Visual selection is
not substituted. Repeating a saved group starts at the current cursor.

Undo boundaries are determined by the individual native actions. The plugin
does not join a group into one undo block.

BUCKETS ~

Git history is partitioned by worktree root and branch. Detached HEADs use the
commit ID. Non-Git buffers use the global current working directory and a
`nongit` label. The worktree HEAD is read for each captured Atom.

Raw Atom history exists only in memory. Each bucket retains `history_size`
entries, and the least-recently-used bucket is removed when `max_buckets` is
exceeded. Saved replay recipes are maintained separately and may persist.

==============================================================================
8. LIMITATIONS                                         *atom-repeat-limitations*

- Replay uses the current buffer, plugin state, and mappings. CmdAtom excludes
  terminal-mode input. A mapping can prompt again if Neovim omitted the keys
  it consumed, for example a direct Vimscript getchar() call. Recording with
  qa ... q also collects prompt keys through the native macro recorder.
- Explicitly selected Ex Atoms are replayed without an extra confirmation.
- Individual Atom payloads have no byte limit.
- Native redo registration is not exposed by the current public Neovim API.
  atom-repeat therefore uses a vim-repeat-style dispatcher around |.|.
- There is no cross-bucket browser, picker integration, named recipes, macro
  export, or existing-Visual-selection substitution.
